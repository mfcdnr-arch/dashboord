# План интеграции с «Базой знаний МФЦ» (ОТЛОЖЕН)

**Статус:** отложено по решению владельца (2026-10-16). Реализацию не начинали. Анализ выполнен, архитектура согласована в общих чертах, открытые вопросы — в конце документа.
**Источник анализа:** архив проекта `call_birkin` (коммит `be62f0e`), сервер базы знаний запускался локально и проверялся вживую.

## 1. Что такое «База знаний МФЦ»

Справочный портал для сотрудников МФЦ ДНР («Мои документы»). Изначально — Artifact на claude.ai, перенесён на собственный сервер.

- **Техника:** Node.js 18+, один файл `kb-portal/server.js` (~580 строк, без зависимостей); весь интерфейс — один `public/portal.html` (~650 КБ); `kb-shim.js` эмулирует Firestore-подобный API поверх REST. Данные — JSON `data/db.json` в памяти, вложения — `data/blobs`. Docker Compose + nginx, Astra Linux, скрипт `./kb`.
- **Каталог услуг:** 144 услуги, 33 ведомства, 5 уровней (федеральные 84, муниципальные 29, региональные 24, иные 4, партнёрские 3), 18 тематических направлений.
- **Карточки услуг:** сроки, пошлины, кто может обратиться, документы, шаги, основания отказа, НПА, FAQ, образцы, памятка заявителю. Цикл: черновик → на проверке → на согласовании → опубликовано → требует обновления → архив; дата пересмотра (по умолчанию 180 дней), куратор, версии с причиной изменения.
- **Разделы материалов:** Новости (с отметкой «ознакомлен»), Нормативная база, Электронные услуги (СПС), Управление очередью, Инструкции по ИС (СМЭВ, ПК ПВД, АИС МФЦ), Бережливые технологии, Записи ВКС; для контакт-центра — FAQ, скрипты диалогов, режимы работы отделений, контакты ведомств. Администратор может добавлять свои разделы (они хранятся как данные в `site/config`).
- **Прочее:** справочник документов, кураторы, файлы с версиями и корзиной, сообщения об ошибках в карточках (новое / в работе / исправлено / отклонено), журнал «что не смогли найти», синонимы поиска, рабочий стол методолога (очереди), для администратора — просмотры, журнал действий, состояние сервера.
- **Роли:** специалист приёма (без входа), специалист КЦ, методолог, администратор.

## 2. Вывод: интеграция возможна (проверено)

- У базы знаний есть HTTP API с дельта-синхронизацией: `GET /api/rev?since=N` — какие коллекции изменились; `GET /api/c?p=<коллекция>&since=N` — только изменённые документы + список удалённых (`deleted`).
- Без входа читаются почти все коллекции, включая журналы истории (`history`, `pagehist`, `kcpagehist`, `dochist`, `curhist`) — с датами и действиями (create/save/publish/archive…). Закрыты только `settings`, `acks`, `roles`.
- Только администратору: `/api/stats` (просмотры по дням), `/api/audit` (журнал действий), `/api/sysinfo`.
- Изменяющие запросы требуют заголовок `X-KB: 1`. Сессии — в памяти: после перезапуска базы знаний все разлогинены и меняется `boot`.
- **У нас внешних коннекторов пока нет** — данные входят только через загрузку файлов (`docs/requirements.md`: «Внешние авто-коннекторы (БД/API) — позже»). Это будет первый коннектор.

## 3. Что можно учитывать на дашбордах

| Вопрос | Источник |
|---|---|
| Что есть (по типу × разделу/теме × статусу) | коллекции материалов и карточек |
| Что появилось и когда | журналы истории: create/publish с датами |
| По каким темам | разделы/подразделы материалов; направление/ведомство/уровень карточек через код услуги |
| Актуальность | просроченный пересмотр, «требует обновления», без даты пересмотра |
| Согласование | очередь и время «отправлено → опубликовано» |
| Качество | открытые сообщения об ошибках, время закрытия |
| Пробелы в знаниях | топ поисков без результата |
| Востребованность | просмотры (нужен админ-доступ к базе знаний) |
| Ознакомление с новостями | отметки «ознакомлен» (знаменатель — наш справочник подразделений) |

## 4. Выбранная архитектура

Варианты: (А) наш опрос существующего API — **этап 1**; (Б) экспорт-эндпоинт + токен только на чтение в базе знаний — **этап 2, целевой**; отклонены: вебхуки из базы знаний, ручные выгрузки файлов, прямое чтение `db.json`.

```
База знаний (сервер 1, nginx :443)
      ▲ HTTPS по ЛВС, опрос дельты каждые 1–5 мин
наш arq-worker (cron)
      ▼
промежуточный слой: зеркало материалов (исходный JSON целиком)
   + история событий
      ▼
ежедневные выпуски датасетов (агрегаты) + текущий перечень материалов
      ▼
формулы → виджеты, алерты, RLS, экспорт — без изменений
```

- **Миграция 030 (рабочие названия):** `data_sources`, `data_source_runs`, `ext_items`, `ext_item_events`; системный пользователь (в `dataset_releases.created_by` NOT NULL) и объект «База знаний МФЦ».
- **Синхронизация:** `/api/rev` → при `reset` или смене `boot` — полная пересинхронизация (отсутствующее помечается удалённым) → иначе дельта по изменённым коллекциям → раз в сутки восстановление истории, каталог, дневные выпуски → журнал прогона, свежесть, сторож/уведомления.
- **Админка:** экран «Источники данных» — адрес, корневой сертификат, служебная учётка (опц.), «Проверить подключение», «Синхронизировать сейчас», состояние/ошибки, автосоздание дашборда из шаблона.
- **Ссылки на материал в базе знаний:** `#card=<код>`, `#sec=<раздел>&pg=<id>`, `#mode=docs&doc=<id>`.

## 5. Расширяемость: новые разделы, блоки, численные показатели

Решение: **численные показатели сейчас НЕ делаем** (неизвестно, появятся ли). Закладываем только дешёвые меры, которые позволят подключить их позже, в том числе задним числом:

- зеркало хранит исходный JSON целиком + версию адаптера;
- разделы и темы — данные, не код (строка датасета = раздел; привязка по id, не по названию);
- коннектор пропускает незнакомые поля и типы блоков, не падает;
- уведомление «в источнике появились новые поля / типы блоков».

Отложено до реальной потребности (выбрать путь, когда сработает уведомление):
- (а) распознавание чисел в таблицах «параметр — значение» и «фактах» карточек (с пометкой «не распознано» для текста вроде «сверить с НК РФ»);
- (б) передача табличных вложений базы знаний в наш конвейер распознавания (`documents.source_type`, `suggest_mapping`);
- (в) формат `/api/export/v1/indicators` в базе знаний: код, название, единица, период, значение, разрез, источник, ответственный, дата обновления.

Замечание: если появится операционная статистика (обращения, очередь, сроки), её первоисточник — АИС МФЦ / электронная очередь; подключать лучше напрямую, а не через базу знаний.

## 6. Безопасность и риски

- Без входа любой в ЛВС читает почти всё, включая отметки «ознакомлен» с ФИО — стоит закрыть в самой базе знаний.
- Просмотры/журнал — только админ с правом записи; пароли по регламенту 4–6 цифр; после 5 ошибок блокируется логин **и IP** → коннектор не повторяет вход при 401; на этапе 2 — токен только на чтение.
- На свежей установке базы знаний действуют встроенные пароли — сменить до подключения.
- TLS: доверять корневому сертификату базы знаний, проверку не отключать.
- 152-ФЗ: имена авторов/ознакомившихся закрывать RLS или хранить только агрегаты.
- Нет стабильного контракта (структуры живут в HTML портала) → адаптер с версией + контрактные тесты на образцах ответов.
- Базовый каталог (услуги, ведомства, направления, исходный справочник документов) зашит в HTML (`const DATA`, `CARDS`, `DOC_SEEDS`), через API отдаются только изменения → на этапе 1 разбор HTML (хрупко), этап 2 исправляет.
- У материалов нет даты создания — брать из первой версии истории; время удаления база знаний не хранит.
- Журнал изменений базы знаний — 5000 записей в памяти → после долгого простоя полная пересинхронизация.
- Дата `updated` в карточках — строка «ДД.ММ.ГГГГ»; просмотры считаются по суткам UTC.
- Ежедневные снимки — только агрегатов; перечень материалов — один актуальный выпуск.
- В табличном виджете нет колонки-ссылки — нужна небольшая доработка.

## 7. План

- **Этап 1 (без правок базы знаний):** миграция 030; модуль коннекторов + адаптер базы знаний + cron; экран «Источники данных»; 6–8 датасетов (состав, новые, актуальность, согласование, ошибки, поиски без результата, просмотры); шаблон дашборда; контрактные тесты; меры расширяемости из п. 5.
- **Этап 2 (правка базы знаний, ~100–150 строк в `server.js`):** роль `reader` с токеном; `/api/export/v1/catalog`, `/api/export/v1/items?since=` (с датами создания и удаления).
- **Этап 3:** переход к материалу, алерты (просрочки → методологу), состояние базы знаний в «Здоровье системы», автоклассификация тем локально.

**Настройки по умолчанию для старта:** все разделы; только агрегаты, без ФИО; синхронизация раз в 5 минут; один экземпляр; без просмотров.
