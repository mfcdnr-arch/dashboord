# Развёртывание Dashboard на сервере (Astra Linux / ВМ / LAN)

Инструкция по установке системы «под ключ». Главный принцип: **скопировать
архив на сервер → разархивировать → развернуть одной командой** `./install.sh`.

---

## 1. Предпосылки (что должно быть на сервере ДО установки)

Устанавливает администратор сервера один раз (наш скрипт это НЕ ставит):

- **ОС:** Astra Linux Special Edition (amd64) или другой Linux x86-64.
- **Docker Engine** + плагин **docker compose v2** (`docker-compose-plugin`).
  Проверка: `docker --version` и `docker compose version` должны отвечать.
- Пользователь установки — в группе `docker` (или запуск через `sudo`).
- **Время синхронизировано** (NTP): при сбитых часах ломаются подписи пакетов и
  сборка. Проверка: `timedatectl` → `System clock synchronized: yes`.

> **Особенности Astra Linux 1.7** (проверено на боевом сервере 06.08.2026):
> - Движок ставится штатно с DVD-репозитория: `sudo apt-get install -y docker.io`
>   (версия 25.0.5.astra3), затем `sudo systemctl enable --now docker` и
>   `sudo usermod -aG docker <пользователь>` + перезаход в систему.
> - **Compose v2 на DVD НЕТ** — там только `docker-compose` 1.29.2, а это v1,
>   он не подойдёт. Плагин доставляется одним самодостаточным файлом:
>   положить `docker-compose-linux-x86_64` (релиз линии v2 с github.com/docker/compose)
>   в `/usr/local/lib/docker/cli-plugins/docker-compose` с правами `0755` и
>   владельцем `root`. Проверка: `docker compose version` → `v2.x`.
> - **Часы.** Если `timedatectl` показывает `RTC in local TZ: yes`, время будет
>   смещено ровно на величину часового пояса. Лечится одной командой:
>   `sudo timedatectl set-local-rtc 0 --adjust-system-clock`. Службы
>   `systemd-timesyncd` в Astra нет — синхронизацию делает пакет `ntp`
>   (`sudo systemctl enable --now ntp`, проверка `ntpq -p`).
> - В базовой поставке нет `curl`, `wget`, `rsync`, `screen`, `tmux`. Установке
>   это не мешает (скрипты обходятся `python3`, см. `http-lib.sh`), но переносить
>   файлы придётся через `scp` — без докачки при обрыве.
- **Свободные порты** на хосте: `8443` (HTTPS) или `8090` (HTTP), при
  наблюдаемости — `3000` (Grafana), `9090` (Prometheus). Открыть в firewall для LAN.
- Диск: ≥ 5 ГБ свободно (образы + данные).

## 2. Быстрый старт — ОДНА КОМАНДА

```bash
tar -xf Final_v.1.tar        # или: unzip Final_v.1.zip
cd Dashbord
./install.sh
```

Всё остальное — автоматически:
1. проверка Docker/compose;
2. если рядом лежит офлайн-бандл образов `dashbord-images.tar` — загрузка образов
   без сборки (полный офлайн); иначе — сборка образов из исходника;
3. генерация **сильных случайных секретов** в `.env.prod` (пароли БД/MinIO/JWT +
   **временные пароли `admin` и `superadmin` печатаются один раз** — запишите их!);
4. выпуск **самоподписанного TLS-сертификата** (HTTPS в LAN);
5. **авто-накат миграций** БД;
6. запуск всего стека (PostgreSQL, Redis, MinIO, API, worker, web-nginx);
7. **smoke-проверка** работоспособности;
8. **ежедневный автобэкап** — ставится автоматически (systemd-таймер или cron;
   если install.sh запущен без root — напечатает команду для ручной установки).

По завершении в консоли будет адрес веб-интерфейса и временные пароли.

Полезные флаги:
> `./install.sh --no-tls` — по HTTP (адрес `http://<сервер>:8090/`).
> `./install.sh --monitoring` — сразу поднять и наблюдаемость (Prometheus+Grafana+Loki).
> `./install.sh --no-backup` — не ставить расписание автобэкапа.

## 3. Два сценария установки

### Сценарий А — сервер имеет доступ в интернет (проще)
Образы соберутся прямо на сервере из исходника:
```bash
tar -xf Final_v.1.tar && cd Dashbord && ./install.sh
```

> **Нюанс: даже при живом интернете бандл часто предпочтительнее.** Сборка на
> сервере занимает 10–20 минут и грузит машину (npm/pip); бандл — `docker load`
> за минуту. Бандл содержит ровно проверенные образы (воспроизводимость), а
> сборка «на месте» тянет пакеты «на сегодня». В госсетях доступ к Docker Hub
> нередко ограничен прокси — бандл снимает зависимость полностью. Правило:
> интернет хороший и доверенный — можно без бандла; сомневаетесь — кладите
> бандл рядом, install.sh сам выберет офлайн-путь.

### Сценарий Б — сервер БЕЗ интернета (полный офлайн, рекомендуется для Astra)
Образы собираются заранее на машине с интернетом, переносятся на сервер.

**На машине с интернетом (Linux amd64):**
```bash
tar -xf Final_v.1.tar && cd Dashbord
./bundle-images.sh          # → dashbord-images.tar (все образы с Linux-зависимостями внутри)
```
**Перенести на сервер** (флешка/scp) папку `Dashbord` И файл `dashbord-images.tar`
(положить `dashbord-images.tar` рядом с `install.sh`, в корень проекта).

**На сервере (офлайн):**
```bash
cd Dashbord
./install.sh                # обнаружит dashbord-images.tar, загрузит образы и развернёт БЕЗ сборки
```

## 4. Сертификат под конкретный адрес сервера

По умолчанию сертификат выписывается на `localhost`. Чтобы он подходил к адресу
сервера в LAN (браузеры меньше ругаются), задайте имя/IP при установке:
```bash
TLS_CN=mfc.local TLS_SAN=10.0.0.5 ./install.sh
```
Сертификат самоподписанный — при первом входе браузер покажет предупреждение
(принять один раз). Для полного доверия — добавить сертификат `certs/tls.crt` в
доверенные на клиентских машинах (по политике организации).

## 5. После установки

- **Открыть в браузере:** `https://<адрес-сервера>:8443/` (или `http://<адрес>:8090/`).
- **Первый вход владельца:** логин `superadmin`, временный пароль — из вывода
  установки. Система **потребует сменить пароль** при первом входе.
- Учётная запись `admin` — тоже с временным паролем из вывода.
- **Роль «Суперадминистратор»** — управление любыми пользователями, включая
  администраторов (сброс пароля, блокировка, роли).
- Дальше администратора встречает **Мастер первичной настройки** (отделы →
  пользователи → объект → загрузка данных → дашборд) — проведёт за руку.

---

## 6. Наблюдаемость (опционально)

Мониторинг метрик/логов (Prometheus + Grafana + Loki). Проще всего — при установке:
`./install.sh --monitoring` (образы мониторинга уже включены в офлайн-бандл
`bundle-images.sh`, так что работает и на изолированной Astra).

Вручную ПОСЛЕ основного стека:
```bash
docker compose -f docker-compose.monitoring.yml --env-file .env.prod up -d
```
- Grafana: `http://<сервер>:3000` (логин `admin`, пароль `GRAFANA_PASSWORD` из `.env.prod`).
- Prometheus: `http://<сервер>:9090`.
- Готовый дашборд «Dashboard — обзор» (запросы/сек, p95-латентность, ошибки 5xx, логи).

## 7. Эксплуатация

### Бэкап данных
Ежедневный автобэкап **ставится install.sh автоматически**. Вручную:
```bash
./backup.sh                       # разовый бэкап (БД + MinIO) в ./backups/
sudo ./backup-schedule.sh install # расписание (systemd-таймер/cron), ротация
```
Каждый бэкап **проверяется на восстановимость** сразу (pg_restore --list + целостность
архива MinIO) — битый набор не останется незамеченным до дня аварии.

**Важно:** задайте в `.env.prod` `BACKUP_DIR` на ОТДЕЛЬНЫЙ диск/раздел или сетевую
папку — бэкап на том же диске не переживёт отказ диска. Настройки: `BACKUP_TIME`,
`BACKUP_KEEP`, `BACKUP_DIR` (после смены — `sudo ./backup-schedule.sh install` повторно).

Восстановление: `./restore.sh <файл-бэкапа>`.

**Если у вас только одна ВМ** — правило: хотя бы одна копия бэкапа должна покидать
машину. Варианты от лучшего к минимальному:
1. **Второй виртуальный диск** от гипервизора (10–20 ГБ) → смонтировать (напр.
   `/mnt/backup`) → `BACKUP_DIR=/mnt/backup/dashbord` в `.env.prod` →
   `sudo ./backup-schedule.sh install` повторно. Отказ основного диска не унесёт
   бэкапы; диск переподключается к новой ВМ.
2. **Сетевая папка** (NFS/SMB на NAS/файл-сервере) как BACKUP_DIR — копии сразу вне ВМ.
3. **Снапшоты самой ВМ** средствами гипервизора (регулярно и обязательно перед
   обновлениями) — защита «машины целиком», дополняет бэкапы данных.
4. **Минимум:** автобэкап складывает наборы в `backups/` на ВМ, администратор
   регулярно забирает свежий набор (`scp -r user@сервер:~/Dashbord/backups/<дата> …`
   или на флешку). Единственный вариант, где копия не уходит наружу сама — нужен
   календарный ритуал.

### Обновление версии
```bash
./backup.sh                       # 1) страховка перед обновлением (обязательный ритуал)
# 2) заменить исходники новой версией (распаковать новый архив поверх), затем:
./deploy.sh                       # 3) пересоберёт образы и накатит ТОЛЬКО новые миграции (идемпотентно)
# офлайн: рядом новый dashbord-images.tar → tar -xf dashbord-images.tar && sh load.sh && ./deploy.sh --no-build
```
Правила обновления:
- **Только из проверенной поставки** (архив + бандл нашего конвейера), не «руками по файлику».
- Данные (БД/файлы) живут в docker-томах и обновлением **не затрагиваются**; `.env.prod`
  и сертификаты лежат вне архива — не перезаписываются.
- Простой — секунды: deploy сам дожидается готовности и прогоняет smoke. После
  обновления взгляните на «Отчёты → Здоровье системы» (всё зелёное).
- Браузеры пользователей обновятся сами (статика с хэшами в именах) — кэши чистить не нужно.
- **Откат:** вернуть прежние исходники/бандл → `./deploy.sh`; данные при необходимости —
  `./restore.sh backups/<набор>/db.dump` из бэкапа шага 1.

### Диагностика / если что-то не так
```bash
./diag.sh                         # сводка состояния (контейнеры, healthchecks, диск, логи)
./smoke.sh 8443 https             # повторная smoke-проверка (или 8090 http)
docker compose -f docker-compose.prod.yml --env-file .env.prod logs api --tail 50
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
```
- **Здоровье системы + автопочинка** — в самом приложении: раздел «Отчёты» →
  «Здоровье системы» (статусы сервисов, латентность, кнопка «🔧 Починить»).
- Упавшие контейнеры Docker перезапускает сам (`restart: unless-stopped`).

### Остановка / удаление
```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod down      # остановить (данные сохранятся)
docker compose -f docker-compose.prod.yml --env-file .env.prod down -v   # + удалить данные (ОСТОРОЖНО)
```

## 8. Полный порядок действий (шпаргалка)

**Офлайн-развёртывание на Astra (типовой случай):**
1. На машине с интернетом: `tar -xf Final_v.1.tar && cd Dashbord && ./bundle-images.sh`
2. Перенести на сервер: папку `Dashbord` + файл `dashbord-images.tar` (рядом).
3. Убедиться, что на сервере есть Docker + docker compose v2, часы синхронизированы.
4. На сервере: `cd Dashbord && ./install.sh`
5. Записать временные пароли из вывода. Открыть `https://<сервер>:8443/`.
6. Войти `superadmin` → сменить пароль → пройти мастер настройки.
7. Автобэкап уже настроен установщиком. (Опц.) мониторинг: `./install.sh --monitoring`
   при установке или поднять вручную (раздел 6).

**Онлайн-развёртывание (сервер с интернетом):**
1. `tar -xf Final_v.1.tar && cd Dashbord && ./install.sh`
2. Далее — пункты 5–7 выше.

### Репетиция без Astra (проверено)
Вся цепочка «bundle-images.sh → офлайн-install.sh → smoke → мониторинг → бэкап»
прогнана END-TO-END на **нативном amd64 Linux** (GitHub Actions, workflow
«Проверка amd64 (бандл + install)», запуск вручную из вкладки Actions): 11/11
образов amd64, стек healthy, rate-limit/gzip/заголовки/Prometheus/Grafana/бэкап —
всё подтверждено. На реальной Astra остаётся только специфика самой ОС
(её версия Docker и офлайн-apt) — механика установки доказана.

## 9. Безопасность (важно)

- Файл `.env.prod` содержит все секреты — **права 600, не копировать наружу, не
  коммитить.** Создаётся автоматически при установке.
- Приватный ключ TLS — `certs/tls.key` (права 600).
- Все временные пароли обязательно сменить при первом входе (система форсирует).
- Система работает в LAN/on-prem; наружу открывать только через контролируемый
  периметр (VPN/firewall).
