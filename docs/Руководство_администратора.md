# Руководство администратора Dashboard

> Документ для администратора/эксплуатации системы. Здесь фиксируются
> административные возможности, эксплуатационные процедуры и **осознанно
> отложенные функции** (что и почему пока не реализовано, что нужно для
> реализации). Обновляется по мере развития проекта.

Кодовое имя: `dashbord`. Отображаемое имя: «Dashboard». Целевая среда:
Astra Linux SE / LAN / часто офлайн. Развёртывание — см. [ДЕПЛОЙ.md](ДЕПЛОЙ.md).

---

## Роли и разграничение доступа (кратко)

- **admin** — полный доступ: пользователи, отделы, роли, объекты, метрики,
  дашборды, аудит, справочники.
- **moderator** — как admin по контенту (объекты/метрики/дашборды/модерация),
  без управления пользователями; редактирует формулы, но **свою** версию формулы
  одобрить не может (разделение обязанностей).
- **senior_moderator** — привилегированная роль просмотра (видит всё как admin/
  moderator при разрешении доступа).
- **user** (обычный пользователь) — видит только выданные ему дашборды
  (опубликованные) и созданные им самим; данные ограничиваются RLS.

Слои разграничения доступа, уже реализованные:
1. **RLS дашбордов** — непривилегированный видит дашборд только по гранту и
   только опубликованным (модерационный гейт).
2. **RLS виджетов (widget-level)** — гранты на отдельные виджеты внутри дашборда
   (миграция 004); при наличии хотя бы одного виджет-гранта зритель-по-гранту
   видит только выданные виджеты.
3. **RLS строк данных (row-level)** — видимость строк датасета по подразделению
   (миграция 024, экран «🔐 Доступ к строкам» у объекта); фильтруются виджетные
   чтения датасета, именованные метрики остаются объективными.

## Разделы интерфейса (что где)

| Раздел | Кому виден | Назначение |
|---|---|---|
| **Главная** | всем | сводка, счётчики, витрина KPI (набор настраивается кнопкой «Настроить»), уведомления |
| **Объекты** | admin/moderator | объекты → папки → документы, распознавание таблиц, выпуск датасетов, канонические поля, «🔐 Доступ к строкам» (row-level RLS) |
| **Метрики** | admin/moderator | формулы (DSL, см. [Инструкция_по_формулам.md](Инструкция_по_формулам.md)), версии draft → validated → approved (свою версию одобрить нельзя) |
| **Дашборды** | всем (по грантам) | конструктор страниц и виджетов, фильтры периода/строки, пресеты, drill-down, экспорт Excel/PDF/PNG, обсуждение, доступ, «📁 Папка» (банк отделов), «В архив», режим «📺 Витрина» (киоск для ТВ) |
| **Витрины** | всем (запись — staff) | именованная подборка из НЕСКОЛЬКИХ ЦЕЛЫХ дашбордов на одном экране («стена мониторов»); порядок — drag-and-drop |
| **Архив** | по допуску | помесячные слепки данных дашборда (переживают ретенцию и удаление дашборда), выгрузка в Excel из замороженных данных, автослепок 1-го числа |
| **Модерация** | admin/moderator | очередь заявок на публикацию, решение «одобрить/вернуть» с причиной и чек-листом, история |
| **Обращения** | всем | тред «пользователь ↔ администратор»; заблокированный пользователь может отправить обращение прямо с экрана входа |
| **Справочники** | admin/moderator | услуги и нормативные документы организации |
| **Пользователи** | admin/superadmin | учётки, роли, отделы, блокировка, сброс пароля, «📊 активность» (единый отчёт: входы + действия + комментарии), «🕵 грант на аудит» (выдаёт только superadmin) |
| **Аудит** | superadmin; admin — по гранту | журнал действий и журнал входов, экспорт CSV/XLSX |
| **Отчёты** | admin/moderator | здоровье системы (CPU/RAM/диск/сервисы, история самопочинок), бизнес-показатели, популярность, качество данных, модерация, посещаемость, логи сервисов (через Loki, если включён мониторинг) |
| **Настройки** | admin/superadmin | пороги свежести/ретенции, вход-блокировка, пороги CPU/RAM/диска, бэкап и автоархив («Запустить сейчас») — **без правки `.env` и рестарта** |
| **Кабинет** | всем | свой профиль, роли, история своей активности, смена пароля |

### Помощники, которые предлагает система

- **«✨ Собрать»** (Дашборды) — автосборка дашборда по объекту: KPI, графики и таблица по числовым полям датасета.
- **«💡 Предложить ещё»** (внутри дашборда) — недостающие виджеты по датасету: система знает, что уже построено, и не предлагает это повторно.
- **«💡 Предложить метрики»** — черновики производных метрик (разница, доля, период-к-периоду, год к году, накопительный итог, план/факт, отклонение от цели). Принятие создаёт **черновик** метрики — дальше обычный цикл draft → validated → approved.
- **Аномалии на графике динамики** — статистическая отметка выбросов (отклонение от линии тренда более N σ, по умолчанию 2). Включается в форме виджета галочкой «Отмечать аномалии». Это статистика (метод наименьших квадратов + стандартное отклонение), **не ИИ**.

## Осознанно отложенные возможности (рекомендации)

Ниже — функции, которые обсуждались и **сознательно не реализованы** на текущем
этапе. Решение принято совместно с заказчиком. Для каждой указаны: суть, причина
отсрочки, предусловия и заметки для будущей реализации.

### 1. Рассылка отчётов (PDF) по расписанию на e-mail (SMTP)

**Суть.** Автоматическая генерация PDF дашборда/отчёта и рассылка получателям по
расписанию (например, ежедневно/еженедельно руководителям).

**Статус:** НЕ реализовано. Отложено.

**Причина отсрочки.** Требуется **рабочий SMTP-сервер МФЦ** (адрес, порт,
учётные данные/релей, политика отправки во внутренней сети / из закрытого
контура). На момент решения SMTP-инфраструктура заказчика недоступна, поэтому
функция блокируется на внешнем предусловии, а не на разработке.

**Что уже готово (фундамент).**
- Экспорт PDF/PNG дашборда на фронте (кнопки «⤓ PDF/PNG»).
- Экспорт данных страницы в Excel.
- Планировщик фоновых задач **arq** (Redis) уже используется (жизненный цикл
  данных: свежесть/ретенция/уведомления) — на нём же можно повесить cron-рассылку.

**Предусловия для реализации.**
- Параметры SMTP МФЦ: host, port, TLS/STARTTLS, логин/пароль или доверенный
  релей, разрешённый адрес отправителя.
- Согласование, кому и что рассылать (список рассылок, привязка к дашбордам/
  ролям/отделам), с учётом RLS: рассылка должна уважать права получателя (не
  отправлять данные, которых он не видит).
- Политика хранения сгенерированных PDF (в MinIO / временно).

**Заметки по реализации (когда появится SMTP).**
- Конфиг SMTP — через переменные окружения (`SMTP_HOST/PORT/USER/PASSWORD/…`),
  секреты в `.env.prod` (не в образ).
- Рендер PDF — переиспользовать существующий экспорт (или серверный рендер
  страницы, чтобы не зависеть от браузера получателя).
- Расписание — задача arq по cron; таблица «подписок на рассылку»
  (дашборд/страница + расписание + получатели + формат).
- **Безопасность:** генерировать PDF от имени получателя (или с проверкой его
  прав), чтобы не обойти RLS строк/виджетов.
- On-prem/офлайн-контур: рассылка только на внутренний SMTP МФЦ; наружу данные
  не отправлять.

### 2. Object-level ACL (ограничение доступа к объекту целиком)

**Суть.** Разграничение доступа на уровне **объекта** (подразделение/филиал/
реестр) целиком: скрыть объект и все его данные/датасеты от пользователей, кому
он не предназначен. Логическое продолжение RLS строк.

**Статус:** НЕ реализовано. Отложено.

**Причина отсрочки.** Текущая модель RLS закрывает основные сценарии МФЦ на трёх
уровнях (дашборд → виджет → строка данных по подразделению). Object-level ACL —
это ещё один, более грубый уровень («видит ли пользователь объект вообще»),
который добавляет заметную сложность (новая матрица доступа объект×субъект и её
проброс во все места чтения объектов/датасетов) при частичном пересечении с уже
готовым row-level RLS. Признано избыточным на текущем этапе.

**Известное ограничение сейчас.** Виджет **«Сравнение подразделений»
(objects_compare)** агрегирует показатель по всем объектам и **не фильтруется**
row-level RLS (это кросс-объектный управленческий срез). Если потребуется скрыть
чужие филиалы даже в этом виджете — это и есть задача object-level ACL.

**Предусловия/что нужно решить перед реализацией.**
- Модель назначения: доступ к объекту по роли и/или по подразделению
  пользователя (аналогично `data_row_acl`, но на объект).
- Opt-in или по умолчанию: объект виден всем, пока не заведено ограничение
  (как row-level), либо закрытая модель.
- Поведение привилегированных ролей (admin/moderator видят все объекты).

**Заметки по реализации (когда понадобится).**
- Заготовка ABAC (миграция 005: `attribute_assignments`/`access_policies` со
  `scope='dashboard'/'metric'/...`) может служить основой, но проще —
  отдельная таблица `object_acl(object_id, department_id|role_id)` по образцу
  `data_row_acl`.
- Точки применения: список объектов (`GET /objects`), чтение папок/документов
  объекта, `objects_compare`, авто-сборка дашборда из объекта, выпадашки выбора
  объекта/датасета.
- Обязательно fail-closed для непривилегированных без назначения.

## Что делать администратору при появлении предусловий

- **Появился SMTP МФЦ** → вернуться к разделу 1: собрать параметры, согласовать
  список рассылок, реализовать cron-рассылку на arq с уважением RLS.
- **Потребовалось скрывать объекты целиком** → вернуться к разделу 2: согласовать
  модель назначения и реализовать object-level ACL по образцу `data_row_acl`.
