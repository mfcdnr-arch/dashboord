# Развёртывание Dashboard (прод)

Целевая среда: **Astra Linux SE / виртуальная машина / LAN**, часто **офлайн**.
Наружу открывается только веб-порт (nginx); PostgreSQL/Redis/MinIO — во внутренней сети Docker.

## Состав
| Файл | Назначение |
|---|---|
| `docker-compose.prod.yml` | прод-стек (пины образов, авто-миграции, только web наружу) |
| `db/run-migrations.sh` | раннер миграций **с трекингом** (`schema_migrations`), применяет каждый файл один раз |
| `frontend/Dockerfile` + `frontend/nginx.conf` | сборка SPA + раздача через nginx с прокси API |
| `deploy.sh` | оркестратор: проверки → сборка → миграции → запуск → smoke |
| `smoke.sh` | пост-деплойная проверка (health/SPA/авторизация) |
| `.env.prod.example` | шаблон окружения (секреты) |

## Предусловия
- Docker + Docker Compose v2, демон запущен, у пользователя есть права.
- **Синхронизированное время** (NTP). Урок с ВМ проекта DS: сбитые часы ломают проверку подписей при сборке/установке.
- Архитектура образов — **amd64** (прод-цель x86-64).

## Онлайн-развёртывание (есть доступ к реестру образов)
```bash
cp .env.prod.example .env.prod
nano .env.prod            # задать POSTGRES_PASSWORD, MINIO_PASSWORD, JWT_SECRET, ADMIN_PASSWORD
./deploy.sh
```
`deploy.sh` соберёт образы, применит новые миграции (перед стартом API), поднимет стек, дождётся готовности и прогонит smoke. Веб-интерфейс: `http://<адрес-сервера>:${WEB_PORT}/` (по умолчанию 8090).

Повторный запуск `./deploy.sh` — безопасен: применит только новые миграции и обновит образы.

## Офлайн-развёртывание (изолированная ВМ)
Собрать/скачать образы на машине с доступом к реестру, перенести архивом, загрузить на цель.

**На машине с доступом:**
```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod build          # api, web
docker compose -f docker-compose.prod.yml --env-file .env.prod pull postgres redis minio
docker save -o dashbord-images.tar \
  dashbord-api:latest dashbord-web:latest \
  postgres:16-alpine redis:7-alpine minio/minio:RELEASE.2022-10-24T18-35-07Z
```
**Перенести** `dashbord-images.tar` + репозиторий на целевую ВМ, затем:
```bash
docker load -i dashbord-images.tar
cp .env.prod.example .env.prod && nano .env.prod
./deploy.sh --no-build       # образы уже загружены — только миграции + запуск + smoke
```

## Пины образов (в `.env.prod`)
- `POSTGRES_IMAGE=postgres:16-alpine`, `REDIS_IMAGE=redis:7-alpine`.
- `MINIO_IMAGE=minio/minio:RELEASE.2022-10-24T18-35-07Z` — **не** `latest`: latest требует CPU x86-64-v2 и падает на старых/generic CPU ВМ.

## Миграции
Применяются сервисом `migrate` (one-shot) **перед** стартом API через `depends_on: service_completed_successfully`.
Раннер ведёт таблицу `schema_migrations` и применяет каждый `db/migrations/NNN_*.sql` ровно один раз (часть ранних миграций не идемпотентна). Новую миграцию достаточно положить в `db/migrations/` — следующий деплой её накатит.

## Диагностика
```bash
docker compose -f docker-compose.prod.yml logs -f api        # логи API
docker compose -f docker-compose.prod.yml logs migrate       # что применилось
docker compose -f docker-compose.prod.yml ps                 # статус/health
./smoke.sh 8090                                              # повторить проверку
```

## Обновление
```bash
git pull            # новый код и/или миграции
./deploy.sh         # пересборка + новые миграции + перезапуск
```

## Эксплуатация (скрипты)
| Скрипт | Назначение |
|---|---|
| `./bundle-images.sh` | собрать api/web **под amd64** и сохранить все образы в `dashbord-images.tar` (для офлайн-переноса с любой машины; нужен `docker buildx`) |
| `./diag.sh` | самодиагностика → `diag-<TS>.tgz` (версии, статус/health, логи всех сервисов, применённые миграции, диск). Приложить к обращению в поддержку. Секреты не включаются |
| `./backup.sh` | резервная копия → `backups/<TS>/{db.dump, minio.tgz}`; ротация `BACKUP_KEEP` (по умолчанию 7) |
| `./restore.sh backups/<TS>` | восстановление из набора (перезапись, с подтверждением). Флаги: `--db-only`, `--minio-only`, `--yes` |
| `sudo ./backup-schedule.sh install` | **автобэкап по расписанию** — ставит systemd-таймер (fallback: cron), ежедневно в `BACKUP_TIME` (по умолч. 03:30). `status` — когда следующий запуск/последний результат; `uninstall` — снять; `print` — показать, что установится (без прав) |

### Автобэкап по расписанию
Вместо ручного cron: `sudo ./backup-schedule.sh install` — определяет systemd и ставит
таймер `dashbord-backup.timer` (`Persistent=true` — пропущенный по выключению запуск
догоняется), иначе добавляет строку в crontab. Время/хранение/каталог — из env или
`.env.prod` (`BACKUP_TIME`, `BACKUP_KEEP`, `BACKUP_DIR`). Проверка: `./backup-schedule.sh status`.
Разовый прогон для контроля: `./backup.sh`.

Артефакты (`backups/`, `diag-*.tgz`, `dashbord-images.tar`) — в `.gitignore`.

## Жизненный цикл данных (планировщик)
Сервис `worker` (arq) содержит cron-задачи:
- **ежедневно 07:00** — проверка свежести: если по объекту нет новых данных дольше `STALE_DAYS` (по умолч. 45), администраторам/модераторам приходит уведомление (колокольчик 🔔);
- **вс 03:00** — ретенция: удаляются релизы датасетов с периодом старше окна `RETENTION_MONTHS` (по умолч. 12 мес; `0` — выключить). Каскадом чистятся значения/поля/связи.

⚠️ Ретенция **удаляет** старые данные. Перед первым включением проверьте объём:
`POST /maintenance/retention/preview?months=12` (роль admin) → сколько релизов/значений попадёт под удаление. Ручной запуск: `POST /maintenance/retention/run`. Ad-hoc проверка свежести: `POST /maintenance/freshness/check?stale_days=N`.

Для работы планировщика сервис `worker` должен быть запущен (он есть в `docker-compose.prod.yml`).

## Безопасность (текущее состояние / на будущее)
- Секреты — только в `.env.prod` (в `.gitignore`). Смените `ADMIN_PASSWORD` после первого входа.
- **Парольная политика (реализовано):** при смене/сбросе/создании пароля пользователя проверяются длина (`PASSWORD_MIN_LENGTH`, по умолч. 8), сложность (буквы+цифры, `PASSWORD_REQUIRE_COMPLEXITY`), совпадение с логином и список распространённых слабых паролей. Не применяется к первичному `ADMIN_PASSWORD` из bootstrap.
- **Резервное копирование (реализовано):** `backup.sh` + автоматизация `backup-schedule.sh install` (systemd-таймер/cron), см. раздел «Автобэкап по расписанию».
- **HTTPS в LAN (роадмап, деплой-фаза):** сейчас LAN/HTTP. Для TLS — терминация на обратном прокси (nginx/Caddy) с самоподписанным или внутренним CA-сертификатом; порт `WEB_PORT` тогда за прокси. HSTS/редирект 80→443.
- **MFA / SSO (роадмап):** второй фактор и единый вход — через Keycloak (OpenID Connect) в LAN; интеграция на этапе, когда заказчик подтвердит требование. До этого — стойкие пароли (политика выше) + блокировка входа по журналу `login_events` (данные уже собираются).
