# Развёртывание Dashboard (прод)

Целевая среда: **Astra Linux SE / виртуальная машина / LAN**, часто **офлайн**.
Наружу открывается только веб-порт (nginx); PostgreSQL/Redis/MinIO — во внутренней сети Docker.

## Состав
| Файл | Назначение |
|---|---|
| `docker-compose.prod.yml` | прод-стек (пины образов, авто-миграции, только web наружу) |
| `db/run-migrations.sh` | раннер миграций **с трекингом** (`schema_migrations`), применяет каждый файл один раз |
| `frontend/Dockerfile` + `frontend/nginx.conf` | сборка SPA + раздача через nginx с прокси API |
| `deploy.sh` | оркестратор: проверки → сборка → миграции → запуск → smoke |
| `smoke.sh` | пост-деплойная проверка (health/SPA/авторизация) |
| `.env.prod.example` | шаблон окружения (секреты) |

## Предусловия
- **Железо: 4 vCPU / 8 ГБ ОЗУ / 100 ГБ SSD** — рекомендуемая конфигурация
  (минимум без мониторинга — 2 vCPU / 4 ГБ / 40 ГБ). Подробный разбор
  с замерами — в [Развертывание_на_сервере.md](Развертывание_на_сервере.md), раздел 1.1.
- Docker + Docker Compose v2, демон запущен, у пользователя есть права.
- **Синхронизированное время** (NTP). Урок с ВМ проекта DS: сбитые часы ломают проверку подписей при сборке/установке.
- Архитектура образов — **amd64** (прод-цель x86-64).

## Онлайн-развёртывание (есть доступ к реестру образов)
```bash
./deploy.sh               # .env.prod нет → секреты сгенерируются автоматически
```
Либо задать секреты вручную:
```bash
cp .env.prod.example .env.prod
nano .env.prod            # POSTGRES_PASSWORD, MINIO_PASSWORD, JWT_SECRET, ADMIN_PASSWORD, SUPERADMIN_PASSWORD
./deploy.sh
```
Что `deploy.sh` делает сам (без ручных шагов):
- **генерирует `.env.prod`** через `gen-secrets.sh`, если файла нет (сильные случайные пароли, режим 600); значения `CHANGE_ME` в существующем файле — ошибка деплоя;
- **предполётно проверяет занятость портов** `WEB_PORT`/`HTTPS_PORT` (свой контейнер от прошлого деплоя конфликтом не считается) — понятная ошибка вместо `bind: address already in use`;
- **включает NTP** (`timedatectl set-ntp true`), если время не синхронизировано, и предупреждает при ОЗУ < 4 ГБ;
- **делает бэкап БД перед накатом миграций** при обновлении (если БД от прошлого деплоя уже работает); отключается флагом `--skip-backup`;
- **однократно перезапускает `api`/`worker`**, если API не стал healthy за ~90 с, и только потом сдаётся;
- прогоняет `smoke.sh` (можно отключить `--skip-smoke`).

Флаги: `--no-build`, `--skip-smoke`, `--skip-backup`, `--tls`.
`deploy.sh` соберёт образы, применит новые миграции (перед стартом API), поднимет стек, дождётся готовности и прогонит smoke. Веб-интерфейс: `http://<адрес-сервера>/` (порт 80), а при `./deploy.sh --tls` и через `install.sh` — `https://<адрес-сервера>/` (порт 443; 80 тогда отвечает перенаправлением на https). Порты по умолчанию стандартные: `WEB_PORT=80`, `HTTPS_PORT=443`. Если на сервере 80/443 уже заняты другим веб-сервером, предполётная проверка остановит деплой и подскажет, кто держит порт; тогда задать в `.env.prod` свободные (например, `WEB_PORT=8090`, `HTTPS_PORT=8443` — адрес станет `https://<сервер>:8443/`). Проверка занятости смотрит сокеты ВСЕХ пользователей (`ss`), поэтому видит и apache2/nginx от root.

Повторный запуск `./deploy.sh` — безопасен: применит только новые миграции и обновит образы.

## Офлайн-развёртывание (изолированная ВМ)
Собрать/скачать образы на машине с доступом к реестру, перенести архивом, загрузить на цель.

**На машине с доступом:**
```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod build          # api, web
docker compose -f docker-compose.prod.yml --env-file .env.prod pull postgres redis minio
docker save -o dashbord-images.tar \
  dashbord-api:latest dashbord-web:latest \
  postgres:16-alpine redis:7-alpine minio/minio:RELEASE.2022-10-24T18-35-07Z
```
**Перенести** `dashbord-images.tar` + репозиторий на целевую ВМ, затем:
```bash
docker load -i dashbord-images.tar
cp .env.prod.example .env.prod && nano .env.prod
./deploy.sh --no-build       # образы уже загружены — только миграции + запуск + smoke
```

## Пины образов (в `.env.prod`)
- `POSTGRES_IMAGE=postgres:16-alpine`, `REDIS_IMAGE=redis:7-alpine`.
- `MINIO_IMAGE=minio/minio:RELEASE.2022-10-24T18-35-07Z` — **не** `latest`: latest требует CPU x86-64-v2 и падает на старых/generic CPU ВМ.

## Миграции
Применяются сервисом `migrate` (one-shot) **перед** стартом API через `depends_on: service_completed_successfully`.
Раннер ведёт таблицу `schema_migrations` и применяет каждый `db/migrations/NNN_*.sql` ровно один раз (часть ранних миграций не идемпотентна). Новую миграцию достаточно положить в `db/migrations/` — следующий деплой её накатит.

## Диагностика
```bash
docker compose -f docker-compose.prod.yml logs -f api        # логи API
docker compose -f docker-compose.prod.yml logs migrate       # что применилось
docker compose -f docker-compose.prod.yml ps                 # статус/health
./smoke.sh 443 https                                         # повторить проверку (без TLS: ./smoke.sh 80)
```

## Обновление
```bash
git pull            # новый код и/или миграции
./deploy.sh         # пересборка + новые миграции + перезапуск
```

## Эксплуатация (скрипты)
| Скрипт | Назначение |
|---|---|
| `./bundle-images.sh` | собрать api/web **под amd64** и сохранить все образы в `dashbord-images.tar` (для офлайн-переноса с любой машины; нужен `docker buildx`) |
| `./diag.sh` | самодиагностика → `diag-<TS>.tgz` (версии, статус/health, логи всех сервисов, применённые миграции, диск). Приложить к обращению в поддержку. Секреты не включаются |
| `./backup.sh` | резервная копия → `backups/<TS>/{db.dump, minio.tgz}`; ротация `BACKUP_KEEP` (по умолчанию 7) |
| `./restore.sh backups/<TS>` | восстановление из набора (перезапись, с подтверждением). Флаги: `--db-only`, `--minio-only`, `--yes` |
| `./restore-check.sh [backups/<TS>]` | **проверка бэкапа настоящим восстановлением** во временную базу (рабочую не трогает): таблицы, миграции и число строк сверяются с рабочей базой, архив MinIO — по числу файлов. Без аргумента — последний годный набор. Код 0 — совпало, 3 — есть расхождения (перечислены), 1 — не восстановилось. Итог — `ops-triggers/restore-check.result` и `restore-check.txt` в наборе |
| `sudo ./backup-schedule.sh install` | **автобэкап по расписанию** — ставит systemd-таймер (fallback: cron), ежедневно в `BACKUP_TIME` (по умолч. 03:30). `status` — когда следующий запуск/последний результат; `uninstall` — снять; `print` — показать, что установится (без прав). **Этот же таймер раз в минуту сторожит фоновый воркер** (см. ниже) |
| `./reset-superadmin.sh` | **аварийное восстановление доступа суперадминистратора** (см. ниже) |
| `./worker-guard.sh` | сторож фонового воркера; запускается таймером сам, вручную не нужен |
| `./health-watch.sh` | **сторож доступности — единственный сигнал, уходящий наружу** (см. ниже); запускается тем же таймером сам |

### Потерян пароль суперадминистратора
Из интерфейса это **не восстанавливается по устройству прав**: сбросить пароль
суперадмина вправе только суперадмин, и выдать эту роль — тоже только он.
Правка `SUPERADMIN_PASSWORD` в `.env.prod` с перезапуском **не поможет**: первичная
инициализация не трогает пароль уже существующей учётки. Система при этом продолжает
работать, но операции владельца (удаление дашбордов и показателей, гранты аудита,
самоодобрение) остаются недоступны.

Выход — на сервере:
```
./reset-superadmin.sh                      # если суперадминистратор один
./reset-superadmin.sh --login superadmin   # если их несколько — указать, кого
./reset-superadmin.sh --grant-to ivanov    # если суперадминов не осталось вовсе
```
Скрипт печатает временный пароль **один раз** (аргументом его передавать не нужно и
не следует — остался бы в истории команд), требует смены при первом входе, завершает
все прежние сессии этой учётки, разблокирует её при необходимости и пишет запись в
журнал действий. Заблокированную учётку без явного `--login` не трогает: блокируют
намеренно, и «восстановить» уволенного нельзя случайно.

**Почему это скрипт, а не кнопка.** Граница безопасности здесь — доступ к самой
машине: у того, кто имеет shell на сервере, и так есть прямой доступ к базе. Кнопка
в интерфейсе была бы слабее, а не удобнее.

**Лучше не доводить:** заведите ВТОРОГО суперадминистратора («Пользователи» → создать
и выдать роль). Тогда вы сможете восстанавливать доступ друг другу, не заходя на
сервер. Пока владелец один, система предупреждает об этом на самом экране.

### Замерший фоновый воркер
Docker поднимает упавший контейнер сам, но по «нездоров» (`unhealthy`) — **нет**:
замерший воркер он оставил бы стоять, а с ним встаёт весь конвейер (распознавание
файлов, выпуск данных, уведомления). Поэтому воркер отдельно стережёт
`worker-guard.sh`, который вызывается наблюдателем раз в минуту. Он поднимает воркер,
если тот перестал отмечаться в Redis, не чаще заданного в «Настройках» числа раз в час
(по умолчанию 3), и каждый перезапуск попадает в «Отчёты» → «Здоровье системы» и в
уведомления. Там же его можно приостановить на время обслуживания и сбросить счётчик
попыток. Если сторож ни разу не отмечался, экран об этом скажет — обычно это значит,
что не выполнялась команда `sudo ./backup-schedule.sh install`.

### Если система станет недоступна — кто об этом узнает
Всё, что система сообщает о своём состоянии, она пишет ВНУТРЬ себя: уведомления,
«Здоровье системы», журнал починок. Пока она работает, этого хватает. Но ровно в том
случае, ради которого сигнал и нужен — не отвечает API, лёг веб-прокси, кончилось
место, встал Postgres, — экран, где было бы видно сообщение, и есть то, что не
открывается. Узнали бы, когда кто-то попробует войти.

Поэтому на хосте работает `health-watch.sh`: раз в пять минут спрашивает `/health`
**снаружи** — через веб-прокси и TLS, тем же путём, которым ходит человек. Проверять
API по внутреннему адресу значило бы пропустить самый частый отказ: прокси лёг, а API
при этом жив.

Куда уходит сигнал:
* **системный журнал сервера** — `journalctl -t dashbord-health` (ошибки: `-p err`).
  Этот канал переживает падение чего угодно в самой системе;
* `ops-triggers/health.state` — текущее состояние человеческим текстом;
* `ops-triggers/health.log` — история переходов (не каждая проверка).

Тревога объявляется **с третьей осечки подряд**, а не с первой: сеть моргает, прокси
перезапускается при обновлении, сервер бывает занят — сигнал, поднимающий дежурного
зря, перестают читать, и тогда он не сработает в настоящий раз. Тревога и возврат в
строй объявляются по одному разу, на переходе. На время `./deploy.sh` сторож
глушится сам и включается обратно при любом исходе, включая неудачу.

Различаются четыре исхода, и каждый ведёт к своей починке: сервер не отвечает вовсе ·
веб-прокси отвечает ошибкой 5xx (приложение за ним не поднялось) · на `/health`
отвечает не приложение, а веб-прокси (сломаны маршруты — проверять nginx, а не базу) ·
приложение отвечает, но база недоступна.

Отдельный таймер ставить не нужно: сторож вызывается из того же наблюдателя, который
раз в минуту стережёт воркер, то есть включается вместе с
`sudo ./backup-schedule.sh install`. Заряжен ли он — видно в «Отчёты» → «Здоровье
системы» отдельной строкой; «ни разу не отмечался» там означает, что таймер не
зарегистрирован и наружу не уйдёт ничего.

**Почты и вебхука здесь нет намеренно.** Это новая инфраструктура для закрытого
контура (SMTP-релей, адреса, доступ наружу) — решение эксплуатации, а не правка кода.
Когда канал появится, письмо будет отправляться из функции `notify()` в этом же
скрипте; остальное менять не придётся.

Настройки (env или `.env.prod`): `HEALTH_URL` — что проверять, `HEALTH_INTERVAL` —
шаг в секундах (300), `HEALTH_FAILS_TO_ALARM` — сколько осечек до тревоги (3).

### Автобэкап по расписанию
Вместо ручного cron: `sudo ./backup-schedule.sh install` — определяет systemd и ставит
таймер `dashbord-backup.timer` (`Persistent=true` — пропущенный по выключению запуск
догоняется), иначе добавляет строку в crontab. Время/хранение/каталог — из env или
`.env.prod` (`BACKUP_TIME`, `BACKUP_KEEP`, `BACKUP_DIR`). Проверка: `./backup-schedule.sh status`.
Разовый прогон для контроля: `./backup.sh`.

Артефакты (`backups/`, `diag-*.tgz`, `dashbord-images.tar`) — в `.gitignore`.

## Жизненный цикл данных (планировщик)
Сервис `worker` (arq) содержит cron-задачи:
- **ежедневно 07:00** — проверка свежести: если по объекту нет новых данных дольше окна свежести (по умолч. 45 дней), администраторам/модераторам приходит уведомление (колокольчик 🔔);
- **вс 03:00** — ретенция: удаляются релизы датасетов с периодом старше окна хранения (по умолч. 12 мес; `0` — выключить). Каскадом чистятся значения/поля/связи.
  Оба окна задаются **в интерфейсе**: «Настройки» → «Хранение данных» и «Свежесть данных», значения хранятся в БД и применяются без перезапуска; там же предпросмотр «что именно удалится». В `.env.prod` этих переменных нет намеренно — значение из БД всё равно побеждает, и правка файла молча не давала бы ничего.

⚠️ Ретенция **удаляет** старые данные. Управление — в интерфейсе: «Настройки» → «Хранение данных (ретенция)»:
предпросмотр показывает поимённый список выпусков под удаление (период, объект, датасет, число значений)
и дашборды, которые после удаления останутся без данных; там же ручной запуск с подтверждением и кнопка
«🕓 Проверить свежесть сейчас». Через API то же самое: `GET /maintenance/retention/preview?months=12`,
`POST /maintenance/retention/run`, `POST /maintenance/freshness/check?stale_days=N` (роль admin).

Для работы планировщика сервис `worker` должен быть запущен (он есть в `docker-compose.prod.yml`).

## Безопасность (текущее состояние / на будущее)
- Секреты — только в `.env.prod` (в `.gitignore`). Смените `ADMIN_PASSWORD` после первого входа.
- **Парольная политика (реализовано):** при смене/сбросе/создании пароля пользователя проверяются длина (`PASSWORD_MIN_LENGTH`, по умолч. 8), сложность (буквы+цифры, `PASSWORD_REQUIRE_COMPLEXITY`), совпадение с логином и список распространённых слабых паролей. Не применяется к первичному `ADMIN_PASSWORD` из bootstrap.
- **Резервное копирование (реализовано):** `backup.sh` + автоматизация `backup-schedule.sh install` (systemd-таймер/cron), см. раздел «Автобэкап по расписанию».
- **HTTPS в LAN (реализовано):** `./deploy.sh --tls` (в `install.sh` включён по умолчанию) выпускает самоподписанный сертификат `gen-tls.sh` и подключает оверлей `docker-compose.tls.yml`: TLS 1.2/1.3, HSTS (полгода), редирект 80→443, порт `HTTPS_PORT` (по умолч. 443). Имя/IP сертификата — `TLS_CN`/`TLS_SAN` в окружении **или в `.env.prod`** (задать один раз). Для полного доверия — добавить `certs/tls.crt` в доверенные на клиентах.
  ⚠️ Редирект 80→443 формируется как `https://$host$request_uri` — **без порта**. При портах по умолчанию (80/443) это ровно то, что нужно: набравший `http://<сервер>` попадёт на `https://<сервер>/`. Если же HTTPS пришлось перевести на нестандартный порт (8443) — обычно потому, что 80/443 заняты другим веб-сервером, — перенаправление уведёт на 443, то есть на ЧУЖОЙ сервер (или в пустоту): давайте пользователям только HTTPS-адрес с портом (`https://<сервер>:8443/`), без http-варианта.
- **Блокировка перебора паролей (реализовано):** rate-limit nginx на `/auth/login` (10 запросов/мин с IP) и `/auth/blocked-appeal` (5/мин), плюс блокировка по логину после `login_max_attempts` неудач за `login_lockout_minutes` (пороги правятся в UI «Настройки», не в `.env`). Все попытки входа пишутся в `login_events` (кто/когда/IP/успех).
- **Адрес в журналах (реализовано):** IP в `audit_log` и `login_events` берётся из `X-Real-IP` — nginx перезаписывает его своим `$remote_addr`, поэтому клиент на него повлиять не может. Заголовкам верим только когда запрос пришёл ОТ доверенного прокси: список задаётся `TRUSTED_PROXIES` в `.env.prod` (по умолчанию приватные сети и loopback — адрес контейнера nginx в docker-сети заранее неизвестен). До правки читалось НАЧАЛО `X-Forwarded-For`, то есть то, что прислал сам клиент, и адрес в журнале подделывался одним заголовком (находка аудита, закрыта 16.09.2026).
- **Заголовки безопасности (реализовано):** CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy на всех ответах; `Cache-Control: no-cache` на SPA-оболочке (иначе после обновления браузер тянет удалённые файлы `/assets/*` из кэша), `immutable` на хэшированных ассетах.
- **MFA / SSO:** по решению заказчика (2026-07-25) — **не внедряется** (снято из скоупа).
- **Отзыв сессий (реализовано):** смена или сброс пароля делает ранее выданные JWT недействительными (`users.password_changed_at` + `iat` в токене, миграция 033). Блокировка учётной записи (`is_active=false`) действует немедленно — проверяется на каждом запросе.
- **Зависимости:** версии пинуются в `backend/requirements.txt` и `frontend/package.json`. Перед выпуском поставки прогоняйте проверку известных уязвимостей: `pip-audit -r backend/requirements.txt` и `npm audit --omit=dev` (в `frontend/`). На 05.08.2026 обе проверки чистые.
- **Срок жизни токена:** `JWT_EXPIRE_MINUTES` в `.env.prod` (по умолч. 720 = 12 ч). При компрометации учётной записи достаточно сменить/сбросить пароль (сессии отзываются) либо заблокировать учётку.
