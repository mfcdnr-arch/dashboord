## 1. Общая идея

Корпоративная система дашбордов с админ-панелью:
- **Модератор** собирает информацию: часть вносит руками, часть тянется автоматически.
- Данные загружаются и **модерируются** через панель управления (черновик → на проверке → опубликовано).
- **RLS**: каждый пользователь видит только то, что разрешил администратор.
- **Дашборд рендерится в браузере (HTML)**, интерактивный.
- **Декомпозиция**: каждое значение раскрывается (формула, источник, владелец, свежесть, достоверность, детализация до первички).

## 2. Подтверждённые решения

- [x] **Модульная архитектура кода — ОБЯЗАТЕЛЬНО.** Не один большой файл. Делим на изолированные модули/сервисы: править легче, ошибки искать легче, каждую часть проверяем на работоспособность по ходу написания. (см. раздел 4).

Два механизма: time-series (ряд значений) + as-of снапшоты («как было на дату»). Партиционирование по месяцам, предагрегаты, фоновая очистка/архивация старше года.
  - [x] Решено: **жёсткое удаление** данных старше года (без холодной копии).
- [x] **Прозрачность KPI** — killer-фича: клик по любому числу раскрывает структуру.
- [x] **Модерация перед эфиром** — данные в дашборд попадают только после approve.

## 2b. Согласованные решения (2026-07-11, через опросник)

- **Стек бэкенда:** **Python + FastAPI** (модуль доступа с NestJS портируем на Python; SQL-схемы переносимы как есть).
- **Домен:** **универсальная платформа**, МФЦ ДНР — первое внедрение (движок generic: объекты→папки→файлы→дашборды).
- **Права:** **тонкие — папка→дашборд→виджет + по конкретному пользователю** (модель securable_objects/object_acl + access_grants уже есть). Row-level (по подразделению, ABAC) — отложено до появления подразделений.
- **Ввод данных:** **полный конвейер с авто-распознаванием** таблиц/столбцов/значений (documents→extraction→dataset_releases). Внешние авто-коннекторы (БД/API) — позже.
- **Ретенция:** удаление данных старше 1 года (совместимо со статусом `archived`).
- **Масштаб (из «ответов»):** on-premise, до ~20 пользователей на старте, 30–100 KPI, приоритет — полнота функционала, не скорость MVP.
- **Единицы/валюты:** несколько единиц измерения, валюта — рубль (уточнить при необходимости).

## 2c. Уточнено 2026-07-12: карточка пользователя и аудит входов (модули «Пользователи»/«Отчёты»)

Требования зафиксированы, реализация — по плану (после этапа 4), отдельным этапом «Пользователи + аудит входов».

- **Карточка пользователя при заведении:** отдельные поля **Фамилия / Имя / Отчество** (не одно `full_name`), **Отдел**, а также логин, email, роли, активность. `full_name` оставляем как отображаемое/вычисляемое (ФИО).
- **Отдел — СПРАВОЧНИК:** новая таблица `departments` (отделы организации), у пользователя — выбор из списка (`users.department_id`). Даёт переиспользование, фильтрацию отчётов по отделу и задел на будущий row-level доступ по подразделению (ранее отложенный).
- **Заведение пользователей:** CRUD-модуль `admin`/`users` (создать/редактировать/деактивировать; назначить роли; выдать временный пароль с `must_change_password`). Управляет `admin`.
- **Аудит входов:** фиксировать событие входа — отдельная таблица `login_events` (`user_id`, `ip_address`, `user_agent`, `success`, `created_at`); запись в эндпоинте `/auth/login`.
- **Отчёт по пользователям (FR-8.8–8.10):** «кто / когда / откуда (IP) / сколько раз заходил» — агрегаты по `login_events` (число входов, последний вход, история; фильтры по периоду/отделу/пользователю). Часть **«куда заходил»** (какие дашборды смотрел, рейтинг просмотров) — логируется через `audit_log`/`view`, когда появится **Viewer** (этап 5+); для этого при появлении просмотров задействовать action `view`.

## 2d. Пожелания заказчика 12.07.2026 → детализация этапа 5 и «Главной»

Источник: `Пожелания 12.07.pages` (8 пунктов). Кратко и как учтено:

1. **Сравнение одинаковых таблиц за разные даты** + диаграммы изменений + динамика за произвольный период (выбор из календаря). → Ряд по периодам у нас уже есть (по одному `dataset_release` на период), поэтому включаем оконную `PERIOD_COMPARE` и фильтр-календарь в этапе 5 (виджет «динамика»).
2. Дашборды — удобочитаемые, информативные, эргономичные, лёгкие в поиске/просмотре. → Планка качества Viewer.
3. **«Главная»** с датой, временем, числом дашбордов, числом пользователей (+ доп. блоки).
4. Диаграммы разных видов (круговые, горизонт./вертик., кривые…) по типу данных. → Виджеты на ECharts + автоподбор типа.
5. Админ/модератор сами размещают, где и на какой странице диаграмма. → Конструктор: раскладка виджетов на сетке страницы.
6. Админ/модератор дают **названия страницам**. → Сущность «страница» с именем/описанием.
7. На «Главной» — **кликабельный каталог страниц** с описанием. → Блок каталога.
8. Пересмотреть проект, предложить улучшения. → Постоянная задача архитектора.

**Принятые решения (2026-07-12):**
- **Модель:** `дашборд → именованные страницы → виджеты`. Дашборд группирует тематические страницы; у страницы — имя, описание, сетка (grid) виджетов. Новая сущность **`dashboard_pages`** (dashboard_id, name, description, position, layout jsonb); размещение виджетов — на сетке страницы (пожелания 5–6).
- **«Главная» — ГИБРИД:** базовые блоки фиксированы, набор ключевых KPI на главной выбирает админ.
- **Блоки «Главной» (MVP, все четыре):** (а) обзор — дата/время/приветствие + счётчики (дашбордов/объектов/метрик/пользователей); (б) **каталог страниц** — кликабельный список с описанием (пожелание 7); (в) ключевые KPI (значение + динамика ↑↓ + спарклайн) + сработавшие KPI-алерты; (г) активность — лента «что нового», популярные/избранные, свежесть данных.
- Зависимость: «число пользователей» и «популярные по просмотрам» опираются на модуль «Пользователи + аудит входов» (§2c, отложен) — на «Главной» показываем доступное сейчас, эти показатели включаем после аудита.

## 3. Стек (финализирован)

- Backend: **FastAPI (Python)**, строго модульно (пакеты/роутеры/сервисы/тесты по доменам)
- Frontend: **React + TypeScript** (viewer + админка); графики — **Apache ECharts**
- БД: **PostgreSQL 16** — единственное хранилище (мета, права, метрики, данные, версии, архив)
- Кэш/очереди/воркеры: **Redis** (+ фоновые задачи: извлечение документов, пересчёт метрик, очистка архива)
- Файлы: **MinIO** (хранение загруженных документов)
- Всё в **Docker**, автоустановка на железо (как в проекте DS)

## 4. Принцип модульности (правило разработки)

Строим НЕ монолитным файлом, а как набор изолированных частей:

- Backend — по модулям/роутерам: `auth`, `access` (RBAC/RLS), `ingestion`, `moderation`,
  `metrics`, `dashboards`, `archive`, `admin`, `notifications`. Каждый — своя папка/роутер/сервис/тесты.
- Frontend — по фичам (feature-sliced): каждый экран/виджет — отдельный компонент.
- Каждый модуль **пишем и проверяем на работоспособность отдельно**, до перехода к следующему
  (smoke-проверка + мини-тест), чтобы ошибки ловились локально.
- Никаких «богов-файлов» на тысячи строк.

## 7. Бэклог доработок дашбордов (2026-07-12) — напоминание, делать позже

Зафиксировано по итогам архитектурного ревью расширенного блока дашбордов.
Порядок реализации (рекомендованный): П1 → сверху вниз.

### Слабые места / риски (найдены при самопроверке)
1. Нельзя ОТРЕДАКТИРОВАТЬ привязку виджета после создания (сменить датасет/поле/тип) — только удалить и создать заново. Пробел UX.
2. Доступ к дашбордам НЕ разграничен — видны всей организации. В схеме есть тонкие права (`securable_objects/object_acl/access_grants`), но для дашбордов не подключены. Нарушает требование RLS «каждый видит только разрешённое».
3. Шаблон копирует коды датасетов/метрик как есть — если в новом контексте их нет, виджеты дадут ошибку. Нужен шаг «перепривязки».
4. Cross-filter упрощён — фильтр по названию строки одного датасета; метрические виджеты и разные датасеты не связываются.
5. Графики фиксированной высоты в grid — при сильном уменьшении плитки контент подрезается (нужна адаптивная высота ECharts под ячейку).
6. Данные виджетов считаются по одному (N запросов на страницу) без кэша — лучше батч-эндпоинт «данные всей страницы» + короткий TTL-кэш.
7. Публикация не привязана к модерации — любой модератор публикует свой дашборд (правило «в эфир после approve» не enforced; стыкуется с этапом модерации).
