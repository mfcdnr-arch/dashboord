## 1. Общая идея

Корпоративная система дашбордов с админ-панелью:
- **Модератор** собирает информацию: часть вносит руками, часть тянется автоматически.
- Данные загружаются и **модерируются** через панель управления (черновик → на проверке → опубликовано).
- **RLS**: каждый пользователь видит только то, что разрешил администратор.
- **Дашборд рендерится в браузере (HTML)**, интерактивный.
- **Декомпозиция**: каждое значение раскрывается (формула, источник, владелец, свежесть, достоверность, детализация до первички).

## 2. Подтверждённые решения

- [x] **Модульная архитектура кода — ОБЯЗАТЕЛЬНО.** Не один большой файл. Делим на изолированные модули/сервисы: править легче, ошибки искать легче, каждую часть проверяем на работоспособность по ходу написания. (см. раздел 4).
- [x] **Архив / временной контур.** Вкладка «Архив»: просмотр данных за любой промежуток в пределах года. Глубина хранения — **1 год** (скользящее окно 12 мес.). Два механизма: time-series (ряд значений) + as-of снапшоты («как было на дату»). Партиционирование по месяцам, предагрегаты, фоновая очистка/архивация старше года.
  - [x] Решено: **жёсткое удаление** данных старше года (без холодной копии).
- [x] **Прозрачность KPI** — killer-фича: клик по любому числу раскрывает структуру.
- [x] **Модерация перед эфиром** — данные в дашборд попадают только после approve.

## 2b. Согласованные решения (2026-07-11, через опросник)

- **Стек бэкенда:** **Python + FastAPI** (модуль доступа с NestJS портируем на Python; SQL-схемы переносимы как есть).
- **Домен:** **универсальная платформа**, МФЦ ДНР — первое внедрение (движок generic: объекты→папки→файлы→дашборды).
- **Права:** **тонкие — папка→дашборд→виджет + по конкретному пользователю** (модель securable_objects/object_acl + access_grants уже есть). Row-level (по подразделению, ABAC) — отложено до появления подразделений.
- **Ввод данных:** **полный конвейер с авто-распознаванием** таблиц/столбцов/значений (documents→extraction→dataset_releases). Внешние авто-коннекторы (БД/API) — позже.
- **Ретенция:** удаление данных старше 1 года (совместимо со статусом `archived`).
- **Масштаб (из «ответов»):** on-premise, до ~20 пользователей на старте, 30–100 KPI, приоритет — полнота функционала, не скорость MVP.
- **Единицы/валюты:** несколько единиц измерения, валюта — рубль (уточнить при необходимости).

## 3. Стек (финализирован)

- Backend: **FastAPI (Python)**, строго модульно (пакеты/роутеры/сервисы/тесты по доменам)
- Frontend: **React + TypeScript** (viewer + админка); графики — **Apache ECharts**
- БД: **PostgreSQL 16** — единственное хранилище (мета, права, метрики, данные, версии, архив)
- Кэш/очереди/воркеры: **Redis** (+ фоновые задачи: извлечение документов, пересчёт метрик, очистка архива)
- Файлы: **MinIO** (хранение загруженных документов)
- Всё в **Docker**, автоустановка на железо (как в проекте DS)

---

## 4. Принцип модульности (правило разработки)

Строим НЕ монолитным файлом, а как набор изолированных частей:

- Backend — по модулям/роутерам: `auth`, `access` (RBAC/RLS), `ingestion`, `moderation`,
  `metrics`, `dashboards`, `archive`, `admin`, `notifications`. Каждый — своя папка/роутер/сервис/тесты.
- Frontend — по фичам (feature-sliced): каждый экран/виджет — отдельный компонент.
- Каждый модуль **пишем и проверяем на работоспособность отдельно**, до перехода к следующему
  (smoke-проверка + мини-тест), чтобы ошибки ловились локально.
- Никаких «богов-файлов» на тысячи строк.
