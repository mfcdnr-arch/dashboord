# Ревизия проекта Dashboard на соответствие правилам

Отвечать по-русски. Заказчик просил проводить это ПЕРИОДИЧЕСКИ (см. [[feedback_review_and_usability]]).
Итог прошлой ревизии — `docs/Ревизия_2026-07-18.md` (образец формата и оценок).

## Ориентиры (по чему сверять)
- `AGENTS.md` (роль-промт архитектора) + рабочие правила в памяти: [[feedback_review_and_usability]], [[feedback_quality_over_speed]], [[feedback_verify_and_document]], [[feedback_language_russian]].
- **Три «максимума»:** система максимально ИНФОРМАТИВНАЯ, максимально АВТОМАТИЗИРОВАННАЯ, максимально УДОБНАЯ для 4 ролей (администратор / модератор / аудит / обычный пользователь).
- **Особый фокус:** создание/настройка дашбордов МАКСИМАЛЬНО в графическом виде — система сама предлагает из ВЫПАДАШЕК, какие документы/датасеты/поля/столбцы/показатели/формулы применить (минимум ручного ввода кодов и синтаксиса).

## Процедура
1. **Прогнать существующее.** Поднять стек (`scripts/dev-api.sh` + preview фронта), `curl /health`, перечислить маршруты (`/openapi.json`), проверить ключевые экраны в браузере. Убедиться, что заявленное в журнале реально работает.
2. **Инвентаризация.** Модули бэка (`backend/app/modules/*`), компоненты фронта (`frontend/src/components/*`), навигация (`App.tsx` — что `ready:false` / «в разработке»).
3. **Оценка по критериям** — таблица со «светофором» (🟢/🟡/🔴): проверка по ходу, ревью, «не перегружено», графичность формул, графичность виджетов, информативность (прозрачность KPI), автоматизация, удобство каждой из 4 ролей.
4. **Что сильно** (не ломать) — коротко.
5. **Пробелы по приоритетам** — сгруппировать: A графичность конструктора; B админ/модерация/аудит; C информативность/прозрачность показателя; D автоматизация/надёжность. Для каждого пункта — конкретная доработка, отметить уже сделанные ✅.
6. **Рекомендованный порядок** доработок (волнами), стыковка с бэклогом §7.
7. **Вопросы на уточнение** пользователю (можно и по ходу работ).

## Форма вывода
- Сохранить документ `docs/Ревизия_YYYY-MM-DD.md` (по образцу предыдущего), обновить статусы ✅ по уже закрытым пунктам.
- В чат — сжатая выжимка: сильные стороны, как применяются правила, главные пробелы, рекомендация + вопрос о направлении (обычно через AskUserQuestion).
- Ничего не «чинить» в этом проходе без отдельного согласия — ревизия отдельно, доработки отдельно (их вести через навык `/ship-feature`).
